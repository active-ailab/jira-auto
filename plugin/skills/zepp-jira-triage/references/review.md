# 审阅与交付

## 评论应让用户读懂

一般按“问题过程 → 原因分析 → 结论”，必要时补一句明确的分析边界或可执行建议。证据就近给原日志位置、源码位置；完整材料、寄存器、候选列表及检索过程留在看板。

崩溃评论最前面保留核心故障原文和精简业务回溯，再讲业务操作、具体访问/调用与代码机制。不要把无关 RTOS/GPU 扫描候选塞进核心调用链。重启类先简述材料范围内多少次、各复位类型多少次、哪些有长按/软件请求等前置事件，再下判断。

分开陈述：

- **已确认的直接机制**：例如保存寄存器、故障指令和异常地址相互对应，目标源码的取项结果未判空。
- **尚未确认的诱因**：例如条目为何为空，是否存在删除/重排失配；有长按事件但无法区分人为按住与按键异常。

不要因为诱因未知，把已经确认的机制也写成完全无法判断；也不能因为直接机制确认，就声称已找到并发、释放后使用或进水等深层根因。

## 待查项要可操作

先穷尽现有日志、截图、dump 与目标代码。不要默认要求用户补交已经提供的文件，也不要堆叠 `key down/up、reset source reg` 等名词让用户猜如何验证。

若现有材料已到上限：写明能确认到哪一步、还不能区分什么，并给具体建议。例如检查按键回弹、在无人按压时观察是否仍触发长按；代码问题则检查取项判空、实际列表长度与业务计数同步，并验证相关操作序列。建议不是已验证的修复结果。

模型执行/输出校验失败要标记 `analysis_failed`，显示具体失败阶段与可续跑方式，不生成可批准的“证据不足根因”。

## 相似问题与发布

通过 Jira CLI 查近期更新的 Bug（包括已解决），比较业务栈、故障指令/地址、线程、对象状态和修复入包情况。历史评论是有出处的线索，不代表本轮解析了历史附件；仅同机型、通用触摸函数或跨版本 PC 相同不足以判重。只能建议真实查到的工单，不自动建立 Duplicate 或流转。

保存准确草稿，确认看板证据快照与飞书卡片对应同一版本。让用户审批；不能替用户点击批准。审批可能在工作期间已发生：结束前读取实际状态，已发布就报告已发布，不再生成“润色版”导致新审批或过期状态。

用户退回时保留原报告和反馈；有具体问题则修订证据或文案。没有新依据不反复推送相同稿件。发布结果未知时只读核对唯一 marker 与原批准正文，禁止自动重发。工单状态流转由用户操作。
