# 文件检查与现场分析

## 每个解包文件都要回答

它是什么、对本问题哪部分有价值、尝试了什么解析、读出了什么、还有什么不能解释。看板材料清单保留此记录；不能只给“二进制，未解析”然后跳过。

| 材料 | 优先检查与价值 | 常见边界 |
| --- | --- | --- |
| 固件日志 | 实际运行版本、用户业务动作、故障/复位、按键、故障前后顺序 | 极少量坏字节不应使整份文件被误判为二进制；保留原文件、UTF-8 容错读取并记录替换数量，损坏字符不能作精确证据 |
| 截图 | 可见界面、提示和用户操作上下文 | 只描述实际看到的内容；静态截图不证明死机时长、线程或堆状态，未提供时不编造 |
| SRAM / PSRAM / PSRAM2 / coredump | 保存寄存器、线程和内存现场、代码匹配、对象状态 | 先确认与同一现场和版本的关联，说明每种内存的实际解析覆盖；文件存在不等于已还原全部堆/线程 |
| 手机日志 | 手机侧连接、同步等辅助信息 | 专用封装未解码与固件文本未读取是两回事；不能仅凭乱码断言加密 |
| `btlg` 蓝牙抓包 | 蓝牙控制器协议、连接行为 | 不是主固件文本或自动等同 ramdump；没有解码器时明确识别结果 |
| 损坏嵌套 ZIP | 尝试有界恢复，判断可否保留部分数据 | 数据流不完整、无 CRC 验证的恢复结果不能冒充完整证据 |

iOS 日志可能为“反馈包 → iOS_DeviceLog → 设备 ZIP → dump ZIP → bin”。现有导入器支持四层嵌套，仍保留总解压大小、文件数、路径及 CRC 限制。dump 时间从内层原始路径优先提取，不能让通用外层反馈包名遮蔽它。

## 版本、符号与源码

使用现有服务的 elf-fetch 集成，不重复输入凭据。崩溃需要 XML/ELF/MAP；只核对重启类型/按键路径时可先只取 XML。已验证 `GenevaW → CI Geneva` 的命名映射，保留工单原机型字段；这不是所有 `W` 后缀都能去掉的规则。

`manifest.xml` 锁定项目和 revision，再 `git show revision:path` 只读取源码；缺对象时按现有只读 fetch 路径获取。Jenkins 调试路径可能来自 `HuamiOS_multi_platform` 或 `HuamiOS_HS3@N/build/../...`，使用现有路径解析器映射到 manifest 项目，不凭本地 HEAD 冒充目标版本。

时间匹配只用于材料关联；版本号相同不等于精确构建匹配。验证故障 PC 所在代码与 dump 的字节，部分段一致不能宣称所有固件段一致。未经明确授权，不为分析而清空工作区或切换用户开发基线。

## 崩溃与重启分开处理

**崩溃：**选定同一 fault/abort 现场，保留核心原文、LF 行号、线程、PC/MTVAL、业务调用路径及目标源码。设备 addr2line 列表可能含扫描候选；普通电源管理 backtrace、GPU/RTOS 候选地址不要全部当作已证明的调用链。完整地址列表留在看板，短评论优先业务路径。

Zepp v1 后续内存 hex 损坏时，现有解析器可保留此前完整且布局正确的首个 RV32 寄存器块，标记 `registers_only`。不能把它说成完整 coredump 解码；已知多个寄存器块不合并。访存计算还必须核对日志 PC 与保存 PC，并区分保存 SP 和架构恢复后的 SP。只有得到对应证据，才能确认“空指针 + 字段偏移 = 异常地址”；不能直接升级为对象释放、并发或内存耗尽。

**重启：**解析 `reset reason {...} 数值` 的实际末尾值，并使用该行自己的枚举。通常 `0:POR`、`3:SOFTWARE`，但以材料中的映射为准；枚举里出现 ASSERT/EXCEPTION 不是发生了对应崩溃。说明读取范围、总记录数和各类型次数，原始全量日志与派生节选不能重复计数。

- `HmReStartScreen` 也可从设置进入；菜单出现本身不证明长按或已执行重启。
- 明确的 `8s pressed` 能支持“日志记录到按键持续有效8秒”，还要结合后续复位；它不能区分人为按住、卡键和电气异常。
- 设置确认 → reboot 请求 → 软件复位记录，可以与 POR 类记录分别解释。
- 只有选定崩溃行段里没有复位记录时，不要把“0次复位”写成整份日志或设备没有重启。

## 已验证经验的使用范围

历史回归覆盖了“少量非法 UTF-8 导致整份固件日志漏读”的问题；也验证了嵌套 dump、机型映射、Jenkins 源码根目录和损坏内存后的寄存器保留路径。这些是流程/解析经验，不是可复制到其他工单的地址、次数或根因。


## 业务数据不更新：沿数据链查证

对心率、血氧等“旧值不刷新/跨天不清空”问题，先读工单操作步骤与预期，区分跨零点失效和滚动24小时，不只围绕标题或附近的蓝牙断言查崩溃。全量日志按 LF 建立“最后有效输出 → 无效/缺失区间 → 服务查询 → UI刷新 → 后续恢复”的时序。

心率 `HRE min hr:`、`HEA_HR get value`、`postEvent` 与 `onHrPoint` 属于不同层次，不能混为“已上报UI”。字段位置、255是否无效、0x20是否未佩戴，需核对目标manifest提交源码；只记录实际可识别条数，不把缺日志或无效值当作传感器从未采样。算法未佩戴状态不证明实际摘表，也不排除识别误判。后来的补测成功要作为恢复/反证单独保留。

分别核对业务服务的缓存清零、无效值通知、UI回调有效值过滤和页面激活重新取值。跨天清零且只通知有效值能形成候选通知缺口，但若激活路径本应清空，必须保留该反证，不能仅靠静态代码宣布截图根因已确认。截图没有可对齐时间时，不声称“补测后仍显示旧值”。

非崩溃问题也应获取对应版本XML并用 `git show manifest_revision:path` 读取业务源码；必要时只读fetch该提交，不以本地HEAD代替。形成有原始日志行号、完整统计范围、目标提交和局限的可审阅补充稿；原已发布评论不自动修改。
