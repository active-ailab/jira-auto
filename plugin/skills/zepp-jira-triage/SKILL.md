# Zepp Jira 问题分析

目标是跑完“工单 → 收集已有材料 → Jira 附件归档 → 文件检查 → 版本/现场/源码分析 → 人工审批”，不是只生成一段结论。常规步骤自行推进，不等用户逐项提醒。Skill 不扩大当前请求的操作范围或授权；仅查询状态时不擅自启动上传或重分析。

## 工作入口

先确定当前服务源码目录（可通过 `JA_SERVICE_DIR` 指定）及 `JA_DATA_DIR`；默认 API 为 `http://127.0.0.1:8791`，局域网看板地址由当前实例配置决定。先读仓库 `AGENTS.md`；服务实现是执行入口，不重复实现认证、分析、上传或审批逻辑。

处理工单时按以下过程推进，现场不足时保留明确边界：

1. **先读当前状态。** 工单详情、描述、已有评论和附件通过 Jira CLI 获取；同时查看服务中的材料、任务、报告和审批状态。已有执行中的任务就跟进，已有成功附件/阶段就校验复用。历史评论是待核实线索，不等于本轮完成的验证。用户已批准发布的版本不要因措辞优化再创建新稿或重复评论。
2. **主动收集质量材料。** 从描述解析对应的质量平台反馈链接。先检查 Jira 已有附件；缺少原始日志时优先让服务的质量采集阶段查询对应反馈并下载；登录失效先从“接入与配置”重连。遇到尚不支持的存储区域或平台功能时，再用反馈的“日志 → 原始日志 → 下载Zip”兜底，核对反馈与工单一致。浏览器会话、下载操作和后台任务衔接见 [收集与归档](references/collection.md)。不要让用户重复提供已经可访问的日志，也不要停在“请自行下载”。真正遇到登录/权限阻塞时说明阻塞点，继续可做的只读检查。
3. **原始包归档到 Jira 后衔接分析。** 本地 ZIP 不等于 Jira 已有附件。使用服务 `import_quality_logs` 路径：检查/解包 → 上传原包 → Jira CLI 重新读到附件 ID → 自动排队分析。不要用旧的 `scripts/import_case.py` 代替该路径。已验证的下载包可用本 skill 的 `scripts/queue_quality_archive.py` 交给现有后台。先检查再提交，随后跟进返回的任务及 `next_run_id`，不能把“已排队”当作完成。
4. **检查每个文件。** 解包后记录每个文件的类型、用途、解析尝试/结果及局限。优先固件日志、截图、ramdump，手机日志和蓝牙抓包按相关性补充。具体格式与取证规则见 [文件与现场分析](references/evidence.md)。质量平台有可取材料而本地为空时停在收集阶段，不能直接生成“用户没有日志/证据不足”的可审批结论。
5. **使用实际现场版本。** 核对工单与日志里的运行版本，区分 OTA 目标版本。调用现有 elf-fetch 获取需要的 XML、ELF、MAP；沿用已验证的机型映射，不能任意去掉机型后缀。源码依 manifest 项目和提交只读读取；不要默认为用户执行 repo sync 或清理工作区。时间对应、版本相同与代码字节匹配是不同证明。
6. **结合业务过程分析。** 崩溃先核心原始日志、故障线程和业务调用路径，再核对指令、寄存器、异常地址、目标代码与前后日志。分别说明“直接故障机制”和“更深层诱因”。重启则按实际复位值分类，核对长按事件、软件 reboot 请求和菜单来源，不能从 POR 直接归因用户误按/进水。只读检索近期相似 Bug，比较实际机制，不能仅凭同机型或跨版本相同 PC 判重。
7. **生成能 review 的准确草稿。** 评论采用简短的“问题过程 → 原因分析 → 结论”，关键证据就近引用；崩溃在前面保留核心日志和精简业务路径。写法与错误示例见 [审阅与交付](references/review.md)。证据有限也要说明已确认什么、哪些诱因未确认；模型执行失败单独标记，不能包装成成功的未知根因分析。
8. **核对交付状态。** 验证附件确实在 Jira，分析运行确实结束，看板保存了材料/证据/版本与当前草稿，飞书审批卡确实发送。审批只能由用户完成；审批后服务按原文评论，工单流转由用户操作。发布结果未知先只读核对唯一标记和正文，不能自动重发。最后核对用户是否已审批，报告实际最新状态。

## 每次结束前

- 没有把现成附件、嵌套 dump 或可读固件日志漏掉，也没有把未实现的解码说成已完成。
- 准确区分后台原始日志采集、浏览器 ZIP 兜底和平台异步解密；登录或区域支持受阻时报告实际阻塞，不泛称未接入。
- 问题过程、直接原因、未确认诱因均有对应证据；不是只罗列工具步骤和材料缺口。
- 待查项说明现有材料的分析边界，建议具体可执行；不默认索取更多日志或要求用户重述操作流程。
- 未绕过人工审批、重复上传未知结果的附件、重复评论、自动判重或流转。

修复新出现的流程/解析问题后，将确实可复用的经验补入相应 reference 和仓库测试；不要把某一工单的地址、次数或结论变成其他工单的默认值。
