# Jira Auto · 本地问题分析工作台

当前版本：0.1.0，个人本机服务与本地 MCP 插件开发版。

## 已实现

- Jira 操作统一通过已初始化的 `jira` CLI；不复制账号密码到服务。
- 每 5 分钟分页发现名下未解决工单，按更新时间增量获取详情。已跟踪工单即使关闭或转出也会继续核对。
- 兼容质量反馈描述字段 `customfield_10513`，回退标准 `description`。
- 从反馈描述提取设备、固件、反馈时间和经过校验的质量平台链接。
- 从网页上传原始日志 ZIP，校验 CRC、限制解压体积与嵌套层数、拒绝越界路径和符号链接。
- Jira CLI 不支持附件文件下载时，使用本机已有 netrc 对固定 Jira 文件地址下载；分析前校验并解包 log/txt/zip/bin，下载失败明确报错。
- 崩溃报告先展示同一现场的核心原始日志与地址栈，再按 ELF 解析函数/行号并从 manifest 提交只读提取源码；忽略正常电源 backtrace，保留栈扫描候选限制。Geneva 支持经内存描述符验证的代码字节比较。
- 飞书专用机器人长连接通知与审批；配置和操作见下文。
- 可读日志搜索，保留文件 ID 与行号。二进制材料单独登记，不伪装为已解析文本。
- 调用 `elf-fetch` 下载 XML/ELF/MAP，验证 XML 的提交锁定、ELF 架构和调试段，记录 SHA256。
- 持久化 SQLite 队列、任务去重、事件时间线、失败和重启中断记录。
- 实时任务过程页：SSE 续传、阶段状态、elf-fetch 工具输出、日志扫描字节/行数、证据文件 ID 和行号。
- 日志导入或新构建材料下载后自动预检，并衔接真实 Codex 根因分析：证据评估、定向检索、交叉核对、待审结论。
- 只读比较固件工作区与目标 XML 中各仓库提交。
- 草稿版本、网页审批、工单/材料变化使审批失效；Jira 回写默认关闭。
- 独立 stdio MCP 插件：查询工单、读取上下文、搜索日志、查询任务、发起准备任务、保存草稿。

## 尚未实现

- 质量平台独立异步解密流程：当前采集原始日志，专用在线解密仍需平台入口。

- 任意平台 ramdump 的完整线程/寄存器解析（已支持的截图会原生传入模型）。
- 自动切换 manifest 与 `repo sync`。现有能力仅核对提交。
- 多用户、远程鉴权、团队共享部署和公共插件目录发布。
- Jira 评论 ID 的自动核对：当前发布通过 CLI，记录唯一发布标记；不声称获得 Comment ID。

## 运行

需要 Python 3.12、uv、jira CLI、elf-fetch、git、readelf。

```bash
uv sync --extra test
uv run jira-auto
```

默认打开 `http://127.0.0.1:8791`。服务只监听 loopback，不直接对公网开放。
`data/` 中包含工单描述、用户日志和本地操作令牌，权限 0700，并被 Git 忽略。

系统服务安装：

```bash
.venv/bin/python scripts/install_service.py
systemctl --user status jira-auto.service
systemctl --user restart jira-auto.service
systemctl --user stop jira-auto.service
```

这是 systemd **用户服务**，随用户会话启动；不保证登出后运行，未开启 linger。
安装脚本不更改 Jira CLI 的 `.netrc`，不存入飞书或模型凭据。
可选私有配置位置：`~/.config/jira-auto/service.env`（自行创建并设置权限 0600）。
Jira 与 elf-fetch 的认证沿用当前用户现有配置。

### 局域网访问

在 `~/.config/jira-auto/service.env` 中配置并重启用户服务：

```ini
JA_HOST=0.0.0.0
JA_ALLOWED_HOSTS=localhost,127.0.0.1,192.168.1.20
```

其他设备访问 `http://<本机局域网IP>:8791`，当前按用户要求无需用户名密码登录（`JA_LAN_AUTH=0`）。
局域网内能连到该端口的人可查看工单、日志并操作工作台；Jira 回写仍默认关闭。
保留 Host/Origin 白名单及写请求 CSRF 校验，不影响正常网页访问。
如后续需要登录，设置 `JA_LAN_AUTH=1` 并重启；账号为 `admin`，密码保存在私有 `data/lan-password`。
本机 loopback MCP 连接保持兼容。当前 HTTP 不加密传输，仍是单用户服务。

## 操作流程

1. 查看同步出的工单，或输入工单号手动导入。
2. 若 Jira 已有日志/ramdump，直接点击“AI 根因分析”，会先下载附件并获取对应版本产物；质量反馈缺日志时自动后台采集并归档 Jira；先在“接入与配置”连接质量平台账号。
3. 在材料页导入 ZIP，点击“XML / ELF / MAP”准备版本产物。
4. 在执行记录中核对任务结果；材料预检后自动进行 AI 根因分析，也可点击工单中的“AI 根因分析”。
5. 检索日志证据，通过插件辅助分析或手动编辑分析草稿。
6. 审阅证据、候选原因、缺口及评论草稿；证据不足或无法判断也有待审结论。材料清单不能审批成根因结论。
7. 启用 `JA_ALLOW_JIRA_WRITE=1` 时，“批准并评论”会审批并立即发布这个已保存版本。新实例默认关闭写入，需由使用者明确开启。未审批时不发布。

发布前会刷新工单并检查快照。如果 CLI 调用超时或失败，状态设为 `publication_unknown`，
禁止自动重发；请在 Jira 查找 `[jira-auto:<report-id>]` 标记。工单流转始终由用户完成。
远端在发布校验与写入之间仍可能发生变化，这是 Jira CLI 缺少条件写入带来的限制。

## 查看执行与分析过程

- 侧栏“执行记录 → 查看过程”，或在工单详情的“执行记录”里打开对应任务。
- 点击同步、版本下载、日志导入或材料预检后，自动打开任务过程页。
- 分享 `/#run=<任务ID>` 可直接回看该任务，记录持久化到 SQLite。
- 日志导入或构建下载触发下一阶段预检时，过程页提供“继续查看材料预检过程”。
- 过程页展示可验证的步骤、工具输出、扫描进度和证据摘要，不生成或伪造模型内部思维链。
- 材料预检是前置规则扫描；“AI 根因分析”会实际调用 Codex 模型。两类任务在界面中区分。
- 质量平台支持后台查询精确反馈、直接下载原始文件并打包；校验解包、将原包上传 Jira、通过 CLI 核对附件清单后继续分析。首次在“接入与配置 → 连接质量平台账号”登录，之后不依赖打开的浏览器。手动 ZIP 导入仍可用。没有取得任何质量材料时，分析停在材料收集，不生成无日志的待审结论。
- 升级前的历史任务保留原记录，不能补造当时未记录的过程。

## 插件开发版

插件目录为 `plugin/`，包含标准 `plugin.json`、`mcp.json` 和 `bridge.py`。
仓库包含 `.agents/plugins/marketplace.json`，供支持本地 marketplace 的桌面客户端发现。
插件只连接 `http://127.0.0.1:8791`，可以通过 `JA_SERVICE_URL` 指定其他 loopback 端口。
运行前需要本机安装 uv 并启动上述服务。首次运行 uv 会解析固定的 MCP SDK 依赖。

也可在 MCP 客户端手动配置：

```json
{
  "mcpServers": {
    "jira-auto": {
      "command": "/home/your-user/apps/jira-auto-service/.venv/bin/jira-auto-mcp"
    }
  }
}
```

六个工具：`list_issues`、`get_issue_context`、`search_logs`、`get_run`、
`request_preparation`、`save_analysis_draft`。没有审批、发布、流转或任意 shell 工具。
插件不能绕过网页审批。具体桌面客户端安装与权限提示需要在目标客户端验证。
公开分发与远程 ChatGPT 使用需要后续部署、认证、权限隔离和平台审核，本开发包不等于已上架。

## AI 根因分析配置与执行边界

- 使用本机 `codex exec` 和现有 ChatGPT 登录；不复制认证文件，不需要另存 API Key。
- `JA_AI_ENABLED=1` 开启模型分析，`JA_CODEX_BIN` 指向 Codex CLI；`JA_AI_PROXY` 可复用本机已有 HTTP 代理。
- 模型沿用用户 Codex 配置中已选择的模型。每轮执行禁用 shell、插件、MCP、浏览器、图像工具和 hooks，仅接收后台提供的证据包。
- 第一轮输出带证据引用的发现与检索计划；后台执行有界的日志和源码检索；第二轮输出结论、事实、候选原因、反证、证据缺口及验证步骤。
- 源码片段同时核对目标 manifest、实际提交及工作区改动。未匹配的源码只作候选线索。
- 系统校验证据 ID。没有直接日志证据或依赖未匹配源码时，不能保留“根因已确认”的结论。
- 四种待审结论：根因已确认、高度怀疑待验证、证据不足、无法判断。模型执行失败生成明确标注受阻且不可审批的错误记录，并将任务标为失败。
- 过程页保留调用生命周期、模型公开发现、检索动作、引用与最终结论；不保存或展示内部 reasoning 项。
- 模型没有 Jira 评论工具。审批/发布由独立后台路径完成；所有真实评论测试仍禁止，测试使用模拟 Jira 发布器。

## 专用飞书 Jira Auto 机器人

使用企业自建应用的机器人能力，通过官方 SDK 长连接接收消息和卡片回调，无需公网回调地址。

1. 在飞书开放平台创建企业自建应用，启用机器人能力，命名为 Jira Auto。
2. 开通 `im:message:send_as_bot`（以应用身份发送消息）和 `im:message.p2p_msg:readonly`（接收用户发给机器人的单聊消息）权限。实际权限名称以控制台为准。
3. 在本机服务目录运行 `.venv/bin/python scripts/configure_feishu.py`，隐藏输入 App Secret；不要把凭据发到聊天或写进 shell 命令。配置位于私有 `data/feishu.json`，权限 600，不进入源码包。
4. 在“事件与回调”启用长连接，事件配置添加 `im.message.receive_v1`，回调配置添加 `card.action.trigger`（卡片回传交互）。发布应用并把自己加入可用范围。
5. 私聊机器人发送脚本显示的 `绑定 jira-auto <随机口令>`。仅私聊匹配口令才会绑定，自动保存 open_id 并删除口令。重新运行脚本会重新绑定，使旧卡片失效。
6. 绑定后，当前及后续待审分析自动推送完整评论。点击“批准并评论”先持久化操作再异步执行，避免回调超时。网页里仍可修改草稿，旧卡片随即失效；过长评论只提供网页审阅入口。

支持私聊“状态”和“帮助”。当前机器人不支持自由对话式分析，也不会让模型代替人审批。
发送、审批、退回及发布结果记录在工单事件中。只允许绑定的 open_id 审批，卡片校验报告版本、消息 ID 和随机令牌。发送不确定、执行中崩溃、Jira 发布不确定均不会自动重试，需在看板核对。应用长期断连会显示待连接状态；服务自动重启退出的飞书子进程。

SDK 1.7.5 的 CARD 帧默认被丢弃，本服务适配器复用原有事件分发及响应路径；测试覆盖实际 SDK 卡片帧到回调和 ACK，不修改 SDK 安装文件。
凭据、绑定和飞书后台配置完成前，只能验证模拟审批流程，不能声称真实飞书收发已验证。

绑定口令遗失时运行 `.venv/bin/python scripts/configure_feishu.py --show-pairing`，只显示当前口令，不修改配置、不重启服务。

## 手动分析列表

首页“＋ 加入分析列表”接受工单号或 `https://jira.huami.com/browse/KEY` 链接，不限负责人。只读取 CLI 有权访问的工单。现有工单行可加入/移出，“分析列表”筛选单独显示已选工单；选择持久化，移出不删除材料、报告或监测历史。加入后可在任务详情查看读取过程，随后打开工单导入材料并运行分析。

已执行的 dump/符号核对结果可登记为 `forensic` 材料（`jira-auto-forensic-v1`），供 AI 引用。原始二进制不会被当作已解析内容；工具报告只支持其中实际核对过的内存、指令和源码。当前仍未实现任意平台 ramdump 的全自动解析。

## 简短评论与相似崩溃检索

新 AI 评论按“问题过程 → 原因分析 → 结论”简短叙述，过程和原因附关键证据位置，末尾仅保留必要补充与疑似同类工单建议。重启次数注明日志范围，区分复位类型和实际触发原因；历史报告保留原文，需显式修订才改变。详细事实、候选原因、验证步骤及模型过程保留在看板“完整分析（不发布至 Jira）”，不会自动塞入评论。

崩溃分析在最终判断前通过 Jira CLI 检索近 90 天更新的 Bug，包含已解决工单。先用函数/源文件/故障地址定向搜索，再补充同机型崩溃检索；读取最多八个候选的描述及最近二十条评论，比较栈帧、指令/访问地址、线程和对象状态。历史评论属于线索，不表示本轮已解析其附件；跨版本 PC 和机型相同不能单独证明同一根因。模型只能建议实际检索到并引用证据的工单，不自动建立 Duplicate 链接或流转。搜索失败标记 partial，不能等价于“没有相似问题”。

模型执行失败单独记录为 `analysis_failed`：界面与飞书明确显示执行失败，不推断“材料不足”，不提供审批按钮；修复后重跑。输出 schema 在调用前递归转换为严格格式，避免新增可选字段导致模型服务拒绝请求。

崩溃类评论先附核心故障日志和精简调用路径，再写代码解释、直接原因与待查诱因。完整地址、内联函数、源码位置和解析范围显示在看板。不要把“直接分配失败已经确认”与“尚未确认泄漏/碎片”混成完全无法判断。

## P0：现场隔离与阶段续跑

- 预处理按启动区段、`last crash` 边界拆分现场，每个现场有固定 ID、线程、分类、版本、LF 行号与时间。支持 assert/abort、malloc failure、load/store fault/HardFault、watchdog timeout/panic；普通电源 backtrace、看门狗初始化和后续非致命告警不会当作同一崩溃。
- dump 文件名的时间与现场 RTC/ramdump 启动时间在 180 秒内且关联唯一时自动选择；时间关联只是候选证据，仍需 ELF 代码比较。多个现场、版本冲突或无法唯一关联时暂停，在工单的“故障现场选择”中选定后再分析。未唯一关联的 dump 不混合解析。
- 支持严格解码 Zepp `#CD` v1 32位格式中的 RISC-V/MHS003、Cortex-M 单线程寄存器及内存区域清单；检查版本、长度和结束标记。未知格式与截断记录明确展示，不声称恢复全部线程或完整堆。RISC-V 与 ARM ELF 按实际架构选择工具，缺失工具会报错。
- 已选现场之外的日志与旧现场工具报告不进入本轮 AI 证据。现场实际版本用于选择产物；manifest 提交用于只读源码导出。历史报告和已批准评论不改写。
- 每轮保存五个阶段：下载与解包、现场分段与关联、版本产物、符号/寄存器/源码、AI分析与草稿。每个阶段记录输入摘要、结果、产物校验、失败原因和复用来源。
- 在执行过程页点击“从失败处继续”，会重新读取 Jira，复用输入相同且 SHA256 校验通过的阶段。材料更新或缓存文件损坏会使对应步骤重做，也可选择阶段强制重跑。成功模型调用按完整证据、提示、结构和模型配置缓存，失败输出不缓存；每次成功分析仍产生新审批版本。
- 服务重启后，执行中的任务标记中断，已完成检查点保留，需手动继续。评论发布不属于续跑流程；发布结果未知时绝不自动重发。

已用 ABS-4233（OOM/abort）与 ABS-4161（load fault）现有材料验证现场关联、coredump寄存器、符号和源码准备。真实问题只读验证不生成审批卡或发布测试评论；边界情况由合成材料测试。

## 证据化审阅、历史版本与补充分析

“分析与审批”按五步展示：故障现场 → 调用链 → 代码解释 → 结论与待查项 → 精确评论文案。默认折叠寄存器、完整帧、源码和历史证据。点击证据编号可跳转到当前报告保存的原始证据；不会使用最新材料替换旧报告的证据。

新分析分别给出“直接故障机制”和“更深层诱因”的判断及证据引用。例如，分配失败导致 abort 可以已经确认，而泄漏、碎片或资源上限仍然未知。旧报告只显示其原有判断，不根据整体置信度推定两层原因均已确认。长调用链保留入口与故障终点，中间省略处显式标记，逐帧数据仍可展开。

- 选择报告版本可回看历史分析，并与上一版本的准确评论对照。历史版本的修改、审批和发布操作关闭；通过报告 URL 可直接回到该版本。
- 修改评论先保存新版本；未保存修改时不能审批。保存后原审批失效。
- “退回并补充分析”要求具体原因，并将该要求传入下一轮 AI。待审/已批准版本会退回；已发布评论保持原样。新结果仍需人工审批。此入口本身不会写 Jira 评论。
- 相似问题区展示历史文本相同点、关键差异和未验证项。公共分配/调度函数不能证明同因；异常机制冲突时禁止建议判重。明确给出的完整修复提交可在本地只读核对目标提交祖先关系，不等价于证明完整固件入包，也不能排除 cherry-pick。
- 排队任务可以取消；执行中的任务不支持强制中止。重复任务选项相同会复用，现场/版本/补充要求不同则明确提示，不会静默丢弃新选项。
- 模型失败区分额度、认证、网络、超时、输出结构和引用校验。执行失败不会被解释成用户材料不足，不允许审批；可保留材料后从 AI 阶段续跑。

看板使用 `compact=1` 只加载选中报告的完整分析，其他历史版本保留摘要，点击后再取；完整 API 保持兼容。本轮 AI 严格使用现场解析阶段返回的产物 ID 和 SHA256，禁止误取同一现场的其他解析版本。证据数量有界时优先保留代码匹配证明与解析局限，避免被大量栈帧挤出。

## 截图与故障访存核对

- Jira 独立 PNG/JPEG/WebP 附件及 ZIP 内图片会校验后登记为截图。单张上限8MiB、1600万像素，仅支持静态图。损坏/不支持的图片明确记录未查看原因，不能伪装成可读日志。
- 每轮最多2张截图按清单顺序作为原始图片输入模型，并提供可引用的证据ID；不靠文件名猜测画面。超额图片记录在未查看清单。图片中的联系方式不应转写到结论；截图与故障现场未建立时间关联时，不能合并为同一事件，也不能从静态图证明卡死时长或内存状态。
- 看板可预览经过校验的原图；历史报告的预览绑定原SHA256，文件变化时拒绝替换。模型缓存也包含图片SHA256，像素变化不会复用旧结论。PNG/JPEG/WebP 校验采用Pillow；Codex使用本机CLI已支持的原始图片输入，shell和其他工具保持关闭。
- Zepp v1 RV32访问异常可对照保存PC、PC处load/store指令、基址寄存器与MTVAL。仅支持明确的常用字节/半字/字load/store形式；不模拟执行、不推断对象生命周期。缺寄存器、PC冲突、未知指令、断言/abort现场都会明确停止该项核对。调整后的SP不当作直接保存的故障基址。
- 例：ABS-4161的`lw a0,20(a5)`、`a5=0`、`MTVAL=0x14`和PC代码字节匹配，可支持空基址访问的直接机制；无法单独证明对象为何为空。ABS-4233的abort PC不会被误解释为非法访存。

验证记录：两单只读真实分析均输出独立的直接机制/深层诱因及6条代码解释；合成截图经真实模型识别文字与色块。网页修改→新版本→补充分析排队→取消已在无执行器、无飞书、无Jira回写的隔离环境验证。原有已发布评论未改写。

发布超时或服务中断导致“发布结果未知”时，可点击“只读核对 Jira 发布结果”。通过 Jira CLI 查找唯一标记，并校验批准文案的每个原始字符（允许 CLI 添加的 Wiki 转义及换行编码差异）。只有唯一标记和文案同时匹配才登记成功；未找到、远端被改写或存在重复标记都保持待核对，绝不自动重发。该核对已在 ABS-4233 的现有评论上只读验证。

分析输入也包括本工单已返回评论页的最多4条历史摘录，每条有评论ID和来源标识，过滤联系方式并限制长度。评论页不完整时明确说明不能保证覆盖最近评论。已有人工分析和机器人旧结论都是待核对线索，不能代替本轮日志、dump和目标源码验证。

加入分析列表会自动排队 AI 分析（AI 关闭时仅预检），包含读取 Jira、下载支持的附件、解包及现场/版本准备；返回的任务直接打开执行过程。列表行显示排队、执行中或失败任务，并可点击查看。重复加入复用进行中的任务或已有记录，不重复分析、不发布评论。旧版本仅保存了选择状态而从未产生分析任务的条目，再次加入时补建任务。

重启类问题会单独提取日志末尾实际复位值，并按该行枚举映射区分 POR、NRST、WDT、软件/异常/断言复位。不会把映射表中出现的 ASSERT/EXCEPTION 当作崩溃。统计范围、用户节选和原始行号均保留；附近的 HmReStartScreen 只作触发链线索，不能直接证明长按、进水或用户误按。没有致命现场但有复位记录时，只下载目标版本 XML 核对按键/复位源码，不强制下载 ELF 或编造调用栈。结论分别解释已知复位类型、候选触发链及区分人为操作/按键卡滞/供电异常所缺的证据。

简短评论保留长度上限内的完整结论和必要限制，不按第一个句号/分号截断，避免丢掉触发链、物理原因的判断边界及下一步验证要求。

附件逐文件检查：按内容识别固件文本、截图、dump 候选、蓝牙抓包和手机日志，看板材料页显示用途与解析结果。极少量非法 UTF-8 字节不会使整份固件日志被丢弃；保留原始文件，以容错方式按 LF 行读取，并记录替换数量。损坏嵌套 ZIP 尝试有限 deflate 恢复，但未完成或未校验 CRC 的内容不视为完整日志。复位分析同时抽取临近长按、设置确认、软件重启请求和硬件复位源记录，不能只凭菜单推断。

质量日志归档通过 `import_quality_logs` 任务完成。Jira CLI 缺少附件上传命令，因此只有附件上传使用固定 Jira 地址的 curl multipart，复用既有 netrc；工单读取和评论继续使用 CLI。上传收据绑定工单和 SHA256；成功可复用，结果未知则禁止自动重传。支持四层嵌套的 iOS 设备 ZIP，dump 时间优先取内层原始路径，避免外层反馈包文件名遮蔽时间关联。质量平台 GenevaW 已核实映射到 CI Geneva；符号和代码字节仍需验证。



可复用分析技能：`plugin/skills/zepp-jira-triage/SKILL.md` 为维护源，本机安装到 `~/.codex/skills/zepp-jira-triage/` 并允许自动匹配 Bug 分析、质量反馈收集和流程排错请求。技能包含质量平台浏览器下载入口、原包归档与后台交接脚本、逐文件检查/现场规则和审批评论写法。`scripts/package_plugin.py` 同时打包该技能，方便同事复用。更新维护源后同步个人安装副本；凭据、真实附件、日志及数据库不属于技能内容。


## 质量平台后台采集

入口为分析任务的“质量日志采集与归档”阶段。Jira 已有日志时优先复用；缺少日志时读取对应反馈，不枚举其他用户反馈。真实下载接口必须同时携带 `id/index/user_id/sync_time`，缺少后两项可能误报 `account_deletion`。采集原始日志、APP、OOM 和 Firebase 可用文件，逐文件检查并保持原始字节，独立 HTTPS 下载不向对象存储发送 SSO 凭据。

- 网页“接入与配置”完成一次 qaplatform 原有 SSO 登录；服务通过一次性、10 分钟有效的回调交换会话，保存在本机 `data/quality-auth.json`（0600）。不导出浏览器 Cookie，不复用 CI Basic 密码。回调票据不进入事件记录，HTTP access log 已关闭。
- 登录失效停止采集，网页显示“需连接账号”；重连后自动续接已选择、因登录失败的任务。日志未就绪、网络异常、CLI 附件清单暂未更新时，每次间隔至少 5 分钟，最多自动续跑两次；之后可人工查看过程并重试。上传结果未知不自动重传。
- 原始文件总下载上限 512 MiB；拒绝 HTML、空文件、长度不完整响应、不支持的存储主机和重定向。已验证的存储包括 Zepp 中国广州、美国 Ashburn COS 桶，以及德国区 S3 path-style 的 `s3.eu-central-1.amazonaws.com/huami-de/`。S3 公共端点同时校验桶名，不放行其他租户；整批下载前先校验每个地址。遇到新区域主机时明确提示未支持，不能关闭校验绕过。
- 任务事件保存查询、文件下载、解包检查、归档和后续分析；工单材料页显示最近采集状态和 Jira 附件 ID。已完成下载按 SHA256 校验复用，反馈身份变化时不能复用旧包。探测下载使用独立状态，不触发上传或新稿。
- 平台“解密日志”仍为另一条异步流程；后台采集成功不代表所有专用二进制格式已经解码。已有文件继续按逐文件价值/解析状态记录。


## 每日优先处理与飞书日期提醒

侧栏“今日优先处理”及总览中的独立推荐区，每天最多列出 3 个你名下、未完成的 Jira。排序为截止日期升序（逾期优先、未设置置后）→ P0/P1/P2 等优先级 → 开始日期升序。尚未到开始日期的任务暂不推荐，除非已到截止日期；不因缺日期虚构排期。

- 北京时间每天 09:00 后，首次完整同步名下工单时确定当天最多 3 个名额，使用已绑定的飞书机器人发一张汇总卡片。今日开始、今日截止、已逾期会明确标出。当天其他工单仅统计数量，不逐条展开或另发日期卡片，遵守用户每天仅 3 项的限制。
- 当天名单确定后不自动补位；完成、转出或改到未来开始的工单从网页隐藏，避免同一天不断增加工单。次日重新排序。09:00 前网页显示预览；当天服务离线后恢复并完成同步，可补发当天卡片，不补发前几天的历史卡片。
- `Start date/customfield_10702` 优先，兼容 WBSGantt 和 Gantt 的开始日期；`duedate` 优先，兼容对应结束日期。基线日期不用于实际计划。Jira Highest/High/Medium 对应 P0/P1/P2，原始名称同时保留；未知优先级显示“未分级”。
- 仅完整且新鲜的名下工单同步快照用于发提醒。手动加入分析列表的他人工单、已解决/完成工单不提醒。网页数据过期时明确提示，等待同步，不用旧快照推送。
- SQLite `daily_focus` 按上海日期保存当天名额、卡片和发送收据。原子领取防止并发重复；发送超时或重启时结果未知则不自动重发。提醒卡片只有 Jira/看板链接，不包含审批、评论或流转操作。
- `/api/focus` 为只读查询，不会启动分析、分配或修改 Jira。服务和飞书进程需在运行中，无需另设桌面自动化任务。

推荐过滤补充：所有类型工单的实际截止日期距今超过 6 个自然月时，不参与每日推荐；恰好满 6 个月仍保留。以截止日期判断，不以创建/最近更新时间判断；未设置截止日期的工单不受该过滤影响。规则升级会重新生成当天推荐，但保留已发送卡片和收据，不额外补发一张卡片。
